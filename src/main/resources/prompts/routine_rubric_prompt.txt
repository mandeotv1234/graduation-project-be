Hard rules:
- Generate 3 to 6 high-quality test cases covering success, invalid inputs, boundary cases, null/empty cases when relevant, and side effects.
- The engine derives expected values by running REFERENCE SQL. Never add expected_result, expected_value, expected_output, or any manually guessed expected field.
- The exam specification DDL is already loaded before every test. setup_script must not CREATE TABLE, ALTER TABLE, DROP TABLE, CREATE FUNCTION, CREATE PROCEDURE, or use GO.
- setup_script is only for test data. Use DELETE/INSERT/UPDATE against existing tables from DATABASE SPEC CONTEXT. Seed every row needed by the routine and helper functions.
- setup_script must be idempotent: before inserting test rows, DELETE the exact keys you will insert because the specification DDL may already contain seed data.
- Before writing setup_script, read DATABASE SPEC CONTEXT and build a foreign-key checklist. For every inserted child row, insert the referenced parent row in the same setup_script first.
- If setup_script inserts ChuyenXe and its TuyenXe column has values such as 'TUYEN01', 'TUYEN02', then setup_script MUST also insert matching rows into [{SCHEMA}].TuyenXe(MaTuyen, ...) before inserting ChuyenXe. This is mandatory even if the procedure only reads ChuyenXe and Xe.
- If setup_script inserts rows into a table with foreign keys, seed parent/master rows first and delete child/detail rows before parent/master rows. Example order: DELETE ChuyenXe, then TuyenXe/Xe; INSERT TuyenXe and Xe, then ChuyenXe.
- Do not rely on existing parent rows from the base dataset. Each test case must be self-contained after its DELETE statements.
- Use [{SCHEMA}].ObjectName for every table, function, and procedure reference. Never use dbo., THIS, TARGET_SCHEMA, YOUR_SCHEMA, or unqualified routine names.
- Do not include schema creation logic. Do not invent tables or columns not present in DATABASE SPEC CONTEXT or clearly used by the reference SQL.
- verification_type must be one of RETURN_VALUE, OUT_PARAMETER, RESULT_SET, SIDE_EFFECT, PRINT_OUTPUT.
- match_type must be EXACT or CONTAINS. Prefer EXACT unless comparing free-form PRINT text.
- Prefer score_weight values that sum to 1.0 across all test cases.
- case_name must be short Vietnamese text for UI display.

Function rules:
- Scalar function RETURN_VALUE: invocation_query should usually be empty, validation_query calls the function, for example "SELECT [{SCHEMA}].fn_Name(1)".
- Table-valued function RESULT_SET: validation_query should SELECT deterministic columns with ORDER BY when order matters.

Stored procedure rules:
- SQL Server stored procedures cannot be queried like tables/functions. Never write "SELECT RETURN_VALUE FROM [{SCHEMA}].<sp>".
- invocation_query must be executable as-is after {SCHEMA} replacement. input_parameters is metadata only; it is not converted into SQL variables by the engine.
- Use concrete literal argument values in invocation_query, for example "EXEC [{SCHEMA}].SP_Name @MaXe = N'XE001'".
- Never write "@MaXe = @MaXe" unless invocation_query declares and assigns @MaXe first, for example "DECLARE @MaXe VARCHAR(10) = 'XE001'; EXEC [{SCHEMA}].SP_Name @MaXe = @MaXe".
- For a procedure that uses RETURN 1 / RETURN 0, use RETURN_VALUE with this same-batch pattern:
  invocation_query = "DECLARE @rc INT; EXEC @rc = [{SCHEMA}].<sp_name> @p1='...', @p2=123; SELECT @rc AS return_value"
  validation_query = "SELECT @rc AS return_value"
- Never write "SELECT return_value FROM @rc". @rc is a scalar variable.
- Prefer RETURN_VALUE for stored procedures that return status with RETURN 1 / RETURN 0. Use PRINT_OUTPUT only when the question explicitly requires grading the printed message.
- Prefer SIDE_EFFECT for procedures that INSERT/UPDATE/DELETE:
  invocation_query = "EXEC [{SCHEMA}].<sp_name> ..."
  validation_query = "SELECT COUNT(*) FROM [{SCHEMA}].<affected_table> WHERE ..."
- PRINT_OUTPUT must have validation_query = "". Do not query PRINT_LOG; no PRINT_LOG table exists. The engine captures SQL Server PRINT messages directly.
- If using a table variable to capture a result set, declare it in invocation_query before INSERT EXEC, then validation_query may SELECT from that same variable.
- If the reference procedure calls helper functions, setup_script must seed the tables those helpers read.
