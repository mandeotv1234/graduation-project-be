=== TEST CASE CREATION RULES ===
1. Create 3-5 different test cases covering scenarios:
   - Single-row INSERT/UPDATE/DELETE (trigger fires normally)
   - Multi-row (common mistake: students assume inserted/deleted has only 1 row)
   - No rows satisfy the condition (trigger should do nothing)
   - If trigger has WHERE/IF: both satisfying and non-satisfying cases
2. Each test case must have a complete setup_script:
   - **CRITICAL - DISABLE FK CONSTRAINTS**: If test case needs to INSERT invalid data (to test trigger validation), MANDATORY disable FK constraints:
     ```sql
     -- Disable FK constraints to test trigger logic
     ALTER TABLE [{SCHEMA}].ChuyenXe NOCHECK CONSTRAINT ALL;
     
     -- ... DELETE and INSERT test data ...
     -- NOTE: ONLY INSERT NECESSARY data, do NOT INSERT data that invocation_query will test
     -- Example: If testing non-existent MaTuyen, ONLY INSERT Xe, do NOT INSERT TuyenXe
     
     -- CRITICAL: do NOT re-enable FK constraints here!
     -- FK will be re-enabled automatically when transaction rolls back after test case
     -- If re-enable, FK constraint will reject instead of trigger, making test case inaccurate
     ```
   - **WHEN TO DISABLE FK**:
     * Test case checks if trigger rejects when foreign key doesn't exist (MaTuyen, MaXe don't exist)
     * Test case checks trigger validation logic (not FK constraint)
     * **NOTE**: With INSTEAD OF trigger, if FK is disabled, do NOT re-enable in setup_script
   - **WHEN NOT TO DISABLE FK**:
     * Test case checks if trigger accepts valid data
     * Test case checks trigger audit log, timestamp, auto-increment
     * Test case checks trigger business logic (2-hour time window, quantity, value, ...)
   - **VERIFICATION_TYPE for test case with disabled FK**:
     * Use "SIDE_EFFECT" instead of "EXECUTION_STATUS"
     * Because EXECUTION_STATUS may be affected by FK constraint if re-enabled early
   - MANDATORY: Start with DELETE to clear old data and avoid duplicate primary key:
     DELETE FROM [{SCHEMA}].ChuyenXe;
     DELETE FROM [{SCHEMA}].TuyenXe;
     DELETE FROM [{SCHEMA}].Xe;
   - Or use DIFFERENT primary keys for each test case (TC_01 use 'T001', TC_02 use 'T002', ...)
   - DROP TABLE IF EXISTS for helper tables (audit log, temp tables)
   - CREATE TABLE with complete structure (if not already in DDL spec)
   - INSERT test data with NON-DUPLICATE primary keys between test cases
   - **CRITICAL**: Check DDL schema context to know EXACTLY table names and column count
   - **CRITICAL**: INSERT must have enough values matching the number of columns specified
   - **CRITICAL**: VARCHAR/NVARCHAR values must be shorter than column length (example: VARCHAR(10) → use 'CX001' not 'CX001_EXISTING')
   - Engine will wrap test case in transaction and rollback, so no cleanup needed.
3. invocation_query: MANDATORY. INSERT/UPDATE/DELETE command to fire trigger.
   Always use this field name; do not output trigger_sql.
   - **CRITICAL**: Must check DDL to know exact column names and data types
   - **CRITICAL**: Number of values in VALUES must match number of columns in INSERT INTO
4. validation_query: MANDATORY for SIDE_EFFECT. SQL SELECT to read side effect result
   (audit table, changed status column, COUNT, ...). Engine will run with reference
   trigger to derive expected_value, then run with student's trigger to get actual
   and compare.
   - For EXECUTION_STATUS, leave validation_query as an empty string because engine
     compares whether invocation_query succeeds or fails.
   - **CRITICAL**: Must use correct column names from DDL schema context
5. Do NOT generate "expected_result"/"expected_value" — engine derives.
6. score_weight is a number 0..1. Sum of all weights is normalized to 1.0 by engine.
7. verification_type for Trigger is almost always SIDE_EFFECT (check data
   after DML). Rarely PRINT_OUTPUT (if trigger has PRINT).
8. **NOTE ON VALIDATION TRIGGER**: If trigger rejects invalid DML using ROLLBACK
   TRANSACTION, THROW, or RAISERROR, invocation_query will FAIL. In this case:
   - Use verification_type: "EXECUTION_STATUS" instead of "SIDE_EFFECT"
   - Set validation_query to an empty string
   - Test case checks if trigger properly REJECTS invalid transaction

**Example 1: Validation trigger with ROLLBACK (constraint checking)**
Suppose DDL has:
```sql

CREATE TABLE Xe (MaXe VARCHAR(10) PRIMARY KEY, BienSo VARCHAR(20), SoCho INT, GhiChu NVARCHAR(100));
CREATE TABLE ChuyenXe (MaChuyen VARCHAR(10) PRIMARY KEY, TuyenXe VARCHAR(10), MaXe VARCHAR(10), BatDau DATETIME, KetThuc DATETIME);
```
