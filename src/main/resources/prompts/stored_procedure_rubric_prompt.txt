1. UNDERSTAND REFERENCE SQL
- Read the user-facing stored procedure body in REFERENCE SQL.
- Identify observable behavior: DML side effects, return code, OUTPUT parameters, SELECT result set, and PRINT messages.
- Test only behavior visible in REFERENCE SQL. Do not invent ideal business rules that the reference procedure does not implement.
- NULL-input failure cases are valid only when REFERENCE SQL explicitly handles that exact NULL parameter before DML, for example "@Param IS NULL", "ISNULL(@Param", "COALESCE(@Param", or TRY/CATCH that returns a stable failure status/message. Do not create a NULL failure case only because a table column is NOT NULL.

2. CHOOSE verification_type
- DML success path: use SIDE_EFFECT. Never use RETURN_VALUE alone for successful INSERT/UPDATE/DELETE/MERGE.
- DML failure/no-change path: use SIDE_EFFECT and prove no unintended data change.
- Read-only SELECT result: use RESULT_SET.
- Status-only procedure: use RETURN_VALUE.
- Main behavior in OUTPUT parameters: use OUT_PARAMETER.
- PRINT behavior: use PRINT_OUTPUT with match_type "CONTAINS" and validation_query "".
- For a DML failure branch that prints only the same generic message such as
  "ERROR" as other branches, do not use that message alone as proof. Prefer a
  SIDE_EFFECT case that proves the intended row state did not change and include a
  branch-specific return code or OUTPUT value when REFERENCE SQL provides one.
- Do not create several indistinguishable PRINT_OUTPUT cases for the same generic
  error text. Their different setup states do not make the observed PRINT output
  branch-specific.
- If a non-DML procedure has no observable state, return code, or OUTPUT parameter
  and several branches only print the same generic error text, keep at most one
  representative PRINT_OUTPUT case for that indistinguishable output. Distinguishing
  those branches requires REFERENCE SQL to expose different error codes or messages.
- If a DML procedure also returns a code or OUTPUT value, include that value in the SIDE_EFFECT validation_query when possible.

3. BATCH, SCHEMA, AND EXECUTION RULES
The engine runs setup_script, invocation_query, and validation_query in one SQL Server batch and one transaction.
Variables declared in invocation_query are visible in validation_query.

- validation_query must not EXEC, EXECUTE, INSERT EXEC, or otherwise call the stored procedure under test again.

4. QUERY PATTERNS
DML procedure:
- invocation_query declares return/output variables and executes the procedure once.
- validation_query SELECTs those variables plus database side effects.
- INSERT/UPDATE success should select affected business columns, not only COUNT(*).
- For DML success cases, derive validation_query from the INSERT/UPDATE/DELETE/MERGE statements in REFERENCE SQL.
- For every INSERT/UPDATE target column that represents business behavior, validation_query must expose that target column.
- This includes columns assigned from input parameters, constants required by the problem, values read from other tables, and calculated values.
- Do not validate only row existence or only a subset of target columns when REFERENCE SQL writes more business columns.
- DELETE success should return a count proving target/related rows are gone.
- Failure/no-change validation must return exactly one row even when no target row exists. Prefer scalar subqueries:
  SELECT @Result AS return_value,
         (SELECT COUNT(*) FROM [{SCHEMA}].<target_table> WHERE <condition>) AS affected_count
- Avoid CROSS APPLY, OUTER APPLY, INNER JOIN, or FROM clauses that can make failure validation return zero rows.

OUTPUT parameter:
- invocation_query declares output variables and passes them with OUTPUT.
- validation_query SELECTs those same variables. Do not redeclare them.

RESULT_SET from stored procedure:
- Capture the result set in invocation_query with a declared table variable and INSERT EXEC.
- validation_query SELECTs from that table variable with stable ORDER BY when order matters.

PRINT_OUTPUT:
- validation_query must be empty.
- Do not create or query PRINT_LOG.

5. SETUP SCRIPT: FOREIGN KEY AND IDENTITY RULES
This is the most important section. setup_script must be executable before invocation_query starts.
Do not only make procedure parameters valid; every row inserted by setup_script must satisfy FK, NOT NULL, and identity rules.

Foreign key context may appear as:
- compact form: "<col> <type> FK-><parent_table>.<parent_col>"
- raw DDL form: "FOREIGN KEY (<col>) REFERENCES <parent_table>(<parent_col>)"
Scan both forms.

For every test case:
1. DELETE in child-to-parent order.
2. INSERT in parent-to-child order.
3. For every setup INSERT, find all FKs where the inserted table is the child.
4. If the inserted row supplies a FK value, the referenced parent row must already exist before that INSERT.
5. Apply this to every setup row, including duplicate/no-change seed rows, not only values passed to invocation_query.
6. For junction/detail/assignment tables with multiple FKs, insert every parent row on every FK edge first.
7. If an inserted parent row also has FK columns, recursively insert its parents first.
8. If the case is not explicitly testing a missing parent/FK condition, all FK-like input parameters used by invocation_query must have valid parent rows.
9. If the case explicitly tests a missing parent/FK, call the procedure with the missing key, but do not insert invalid child rows that violate FK constraints during setup.
10. For circular FKs or self-FKs, only use a setup state that can actually be inserted:
    insert nullable back-reference columns as NULL first, insert the related row, then UPDATE the back-reference.
    If all columns in the cycle are NOT NULL, pick a different scenario instead of creating impossible setup data.

IDENTITY safety:
- SQL Server IDENTITY values are not reset by DELETE and are not rolled back by transaction rollback.
- Never assume a newly inserted identity row receives id = 1, id = 2, or any other guessed literal.
- If a later child row, invocation argument, or validation condition needs an identity key, use one safe pattern consistently:
  A. Explicit deterministic key: wrap only that table's INSERT with SET IDENTITY_INSERT [{SCHEMA}].<table> ON/OFF and insert a unique test id.
  B. Generated key lookup: insert without the identity column, then capture/look up the actual generated id and use that same value in child INSERTs, invocation_query, and validation_query.
- Never mix "INSERT parent without id" with "INSERT child (... parentId) VALUES (1)".
- Never turn IDENTITY_INSERT ON for more than one table at the same time. Turn it OFF before enabling it for another table.

Abstract setup examples; apply the pattern to the actual schema, do not copy table names:
- Normal FK:

  DELETE FROM [{SCHEMA}].Parent;
  INSERT INTO [{SCHEMA}].Parent (parentId, requiredCol) VALUES ('P1', 'ok');
  INSERT INTO [{SCHEMA}].Child (childId, parentId, requiredCol) VALUES ('C1', 'P1', 'ok');
- IDENTITY parent used by child/invocation:
